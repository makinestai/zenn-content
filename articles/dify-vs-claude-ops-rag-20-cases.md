## 1. はじめに：肌診断の次は、中堅企業の社内問い合わせ AI

前回の肌診断 AI を 1 ヶ月作って、唯一捨てなかった資産が「評価ハーネス（品質を 5 軸で数値化する採点スクリプト）」でした。題材を変えても流用できる「測る仕組み」が、1 ヶ月の試行錯誤で手元に残った最大の成果でした。

肌診断のような「学術的に未解決」の領域ではなく、**中堅企業で予算が出ている実需の領域**に、前作で身につけた仕組みで挑むほうが、社会的価値にも届きやすい。そう判断して選んだのが「中堅企業の社内問い合わせ AI（情シス・人事・経費・マニュアル）」でした。

評価ハーネスをそのまま流用して、別ドメインで同じ仕組みでもう一度立ち上がれるか ── 本記事はその実装ログです。前回の記事を読んでいない方でも単独で読めるように、必要な前提（RAG とは / Dify とは / 評価ハーネスとは）は本文中に説明を入れています。

> **ここまでで分かったこと**：1 ヶ月の手探りで残るのは「成果物」ではなく「測る仕組み」だった。題材を変えても、同じ仕組みでもう一度立ち上がれる。

## 2. 何を作ろうとしたか：情シス・人事・経費の質問に答える AI

中堅企業（従業員 100-500 名規模）の社内では、毎日のように同じ質問が情シス・人事・経費に届きます。「VPN がつながらない」「経費精算の領収書のルールは？」「副業申請の手順は？」── これらの 7-8 割は、社内 FAQ や規則文書に答えが書いてあります。ただ、人が文書を探して読むコストが高い。

ここに **RAG（検索拡張生成、Retrieval Augmented Generation = 外部の知識を検索して、その内容を AI に渡して答えさせる仕組み）**[^rag] を使うと、自然な日本語の質問に対して、社内文書を引用しながら答えてくれる AI が組めます。今回はこれを Dify で実装しました。

[^rag]: 前作の肌診断 AI でも RAG を使っていて、あちらは「化粧品の商品情報」と「肌悩み別アドバイス」を引いていました。今回引くのは「社内 FAQ」と「規則文書」と「マニュアル」。題材が変わっても、仕組みは同じです。

公開した OSS は [ops-rag-template](https://github.com/makinestai/ops-rag-template) です。サンプル企業「Sample Corp」（架空の BtoB SaaS、従業員 300 名規模）を想定して、情シス FAQ 8 件 + 人事規則・経費規則・情シスセキュリティ規則 3 種類 + マニュアル 3 ファイル を含めています。実在企業・実在人物の情報はゼロ。

> **ここまでで分かったこと**：社内問い合わせは、知識ベースが「FAQ / 人事 / 経費 / マニュアル」のように分かれていて、それぞれを別の文書セットにできる構造。Dify が得意なパターンだった。

## 3. Dify でできた 4 つのこと

![図1: Dify ワークフロー全体図 (v0.1)](/images/zenn2/01_workflow_diagram.png)
*図 1: Dify ワークフロー（v0.1）。質問を受けて 4 つの Knowledge を並列に検索し、結果を 1 つの応答生成 LLM に集約する。*

### ① 5 つの Knowledge に質問を投げて答える

**Knowledge**（Dify 用語、検索対象になる文書セット）を 5 つ作りました：

| Knowledge | 中身 | 想定する質問例 |
|---|---|---|
| 情シス FAQ | よくある質問 8 件 | 「VPN つながらない」「PC の Wi-Fi が遅い」 |
| 人事規則 | 就業規則・休暇規程 | 「副業申請の手順は？」「有給休暇の繰越ルール」 |
| 経費規則 | 経費精算ルール | 「タクシー代の上限は？」「領収書がない場合」 |
| 情シスセキュリティ規則 | パスワード・端末管理 | 「USB メモリ使ってもいい？」 |
| マニュアル | オンボーディング / 経費フロー / VPN セットアップ | 「入社初日の手順」 |

質問を投げると、Dify が **4 つの Knowledge を同時に並列検索**して、関連する箇所を 3-5 件ずつ拾ってきます。それを Claude Sonnet 4.5 に渡して、引用付きで答えを組み立てる、という流れ。

![図2: Knowledge 一覧（投入後）](/images/zenn2/02_knowledge_list.png)
*図 2: `make ingest` で 5 つの Knowledge が自動作成された状態。チャンク数も Dify Web UI で確認できる。*

### ② ノーコードでワークフローが組める

図 1 の通り、「質問を受ける → 4 つの Knowledge を並列検索 → 検索結果をまとめる → Claude Sonnet 4.5 が引用付きで答える」という流れを、**Studio 画面で線と箱で組み立てる**だけで作れます。Python や YAML を手書きせず、業務に渡せる形まで持っていける。

これは「クライアントの担当者（エンジニアでない方も含む）が運用で触れる」ことを意味します。検索の対象を増やしたい、プロンプトの言い回しを変えたい、というときに、開発者なしで Studio から直接編集できる ── これがノーコードプラットフォームの本領です。

### ③ Claude Sonnet 4.5 に検索結果を渡す

Knowledge 検索の上位 3 件を Claude Sonnet 4.5 に渡し、引用元を明示しながら答えます。応答末尾には「【出典】faq_001」のように、参照した文書 ID が付くようにプロンプトで指示しました。

Claude には **Prompt Caching**（プロンプトの前半を AI 側にキャッシュさせて、2 回目以降の呼び出しコストを下げる仕組み）を効かせています。同じ system プロンプトが何度も使われる業務 RAG では、この機能が効きやすい。

### ④ クライアントが自分で調整できる

Dify Studio では、各ノードのパラメータ（検索結果の取得件数、類似度のしきい値、Claude に渡すプロンプト、応答の最大長など）をブラウザ画面で変えられます。コードのデプロイなしで、運用しながら微調整できる。

これは中堅企業の社内 AI 案件で **保守の引き渡しコスト**が下がる大きな利点です。エンジニアが常駐できない現場でも、Studio の使い方さえ教えれば、現場担当者がチューニングできる。

> **ここまでで分かったこと**：Dify は「Knowledge を作る → ワークフローで繋ぐ → 公開する」までが Studio 画面で完結する。コードはほぼ書かずに、業務に渡せる形まで持っていけるのが効く。

## 4. 実装でハマったこと：Dify v1.x の設定ファイル仕様

評価ハーネスで Dify ワークフローを動かす前に、設定ファイル（Dify のワークフローを YAML 形式で書いたもの、Dify では「DSL」と呼ばれる）のインポートで数回ハマりました。

具体的にハマったのは以下：

- 設定ファイルのバージョン番号が古かった（v0.1.0 → v0.3.0 に上げる必要）
- 環境変数の自動解決が効かず、データベース固有の長い ID 文字列を直接書く必要があった
- Claude のモデル名は短縮形ではなく日付サフィックス付き（`claude-haiku-4-5` ではなく `claude-haiku-4-5-20251001`）でないと認識されない
- ノード間を繋ぐ線（edges）に必須フィールドが欠けていてエラー
- ワークフローモードのアプリは別の API エンドポイントを叩く必要があった

エラーメッセージだけでは原因が分からず、ブラウザの開発者ツールのコンソールを見たり、Dify 公式のソースコードの中の型定義を直接読んだりして、ようやく必須フィールドの全貌が分かりました。**公式 docs が追いついていない領域は、ソースコードを読む覚悟が必要**——というのが最大の学び。

正規型として動く設定ファイルは [`dify/workflow.yml`](https://github.com/makinestai/ops-rag-template/blob/main/dify/workflow.yml) に置いたので、fork する方は同じハマりを踏まずに済むはずです。技術的な詳細（必須フィールドの一覧、エラーメッセージの読み方、ノードごとの注意点）は OSS の [`dify/README.md`](https://github.com/makinestai/ops-rag-template/blob/main/dify/README.md) に整理しました。

> **ここまでで分かったこと**：Dify v1.x の設定ファイル仕様は公式 docs だけでは追いつかない部分があり、必要に応じてソースコードを読む覚悟がいる。詳細は OSS リポジトリの README に書いた。

## 5. 動かしてみての評価：Dify で組んだ社内 AI の品質

評価ハーネス（品質を 5 軸で数値化する採点スクリプト）は Zenn 1 で実装しています。今回はこれを Dify ワークフローに向けて流用しました。20 ケースの想定質問を投げて、応答の品質を **judge（採点役の AI、別の AI が応答を採点する仕組み）** が 5 軸で採点します。

| 軸 | 配点 | 採点内容 |
|---|---|---|
| accuracy（正確性） | 50 | 引用した文書の内容と応答が一致しているか |
| coverage（網羅性） | 20 | 質問が複数の論点を含むとき、すべてに触れているか |
| tone（応答のトーン） | 10 | 中堅企業の社内 AI として適切な丁寧さか |
| latency（応答時間） | 10 | 3 秒以内 10 / 5 秒以内 5 / それ以上 0 |
| cost（API 課金） | 10 | ¥10 以内 10 / ¥30 以内 5 / それ以上 0 |

20 ケースの内訳：情シス FAQ 8 + 人事規則 5 + 経費規則 5 + マニュアル参照 2。判定は Claude Sonnet 4.5 自身が judge を担当します（別の AI を採点役に立てる構成）。

### 結果

| 指標 | 実測値 |
|---|---|
| 総合スコア（100 点満点、20 件 mean） | **89.10** |
| 総合スコア（中央値 / 最小 / 最大） | 90 / 83 / 90 |
| 応答時間（中央値） | 17.80 秒 |
| 1 件あたりコスト | ¥3.91（mean） |
| コンプライアンス pass 率 | 100%（個人情報リーク・不適切な業界言及なし） |

![図3: 評価結果ダッシュボード](/images/zenn2/03_eval_dashboard.png)
*図 3: 20 ケース個別のスコア分布とカテゴリ別の breakdown。生成は `scripts/compare_modes.py`。*

カテゴリ別の傾向：

| カテゴリ | 件数 | 平均スコア |
|---|---|---|
| 情シス FAQ | 8 | 89.75 |
| 人事規則 | 5 | 89.20 |
| 経費規則 | 5 | 87.60 |
| マニュアル参照 | 2 | 90.00 |

すべてのカテゴリで 87 点以上、応答時間は中央値 17.80 秒。中堅企業の社内 AI として、まず **PoC（Proof of Concept、本番投入前の概念実証）** に持っていける品質帯に着地しました。「数字で語れる」という意味で、案件の説得材料にも、改善の出発点としても使えます。

> **再現条件の注意**：サンプルデータが英語混じりの製品名（GlobalProtect、ServiceNow 等を「製品カテゴリの代表例」として混入）を含むため、完全な日本語ドキュメントで構成された自社の Knowledge では、accuracy 軸でやや下がる可能性があります。20 ケースという小さなサンプルサイズに対しては、±5 点程度の振れ幅を見込んでください。

> **ここまでで分かったこと**：評価ハーネスで Dify の品質を「数字」で語れるようになった。PoC から本番に渡すときの説得材料として使える。

## 6. 学びと、次に作るもの

実装で得た学びは 3 つ。

**① ノーコードで「業務に渡せる形」まで届く**：Dify は Knowledge を作るところから、ワークフローを組むところ、公開してエンドポイントを返すところまで、Studio 画面で完結します。クライアント側の担当者が運用しながら微調整できる、というのが業務 AI として本領発揮するポイント。

**② 評価ハーネスは題材を変えても流用できる**：肌診断 → 社内問い合わせと、題材は大きく変わりましたが、5 軸ルーブリック + judge プロンプトの差し替えだけで baseline が取れました。「題材を作る」より「測る仕組みを作る」ほうが長期リターンが大きい、という Zenn 1 の主張が、別ドメインでも成立することを確認できた。

**③ 公式 docs より型定義のソースコード**：Dify v1.x のような速く更新されるツールでは、公式 docs が追いつかない領域があります。設定ファイルの必須フィールドに迷ったら、ソースコードの型定義を直接読むのが最短経路でした。fork する方が同じ道を辿らずに済むよう、本リポジトリの `dify/workflow.yml` を「正規型」として保持しています。

## 補足：素の Claude SDK で直接組んだ場合との比較（参考）

参考までに、Dify を使わず Anthropic SDK で同じ 20 ケースを回した数値も載せておきます。Sample Corp 規模（5 ファイル ≈ 17K トークン）だと、Knowledge を全件 system プロンプトに詰めるだけの素朴な構成でも回ります。

| 指標 | 素の Claude SDK | Dify ワークフロー |

数字だけ見ると素の SDK のほうが速く安く済んでいますが、Knowledge が数十〜数百ファイルに増えると、素朴に全件 system プロンプトに詰める方式は破綻します（プロンプトの長さに上限がある、長くなるほど単価が上がる、検索の精度が落ちる）。

Dify は「ノーコードで運用に渡しやすい」「Knowledge が増えても応答プロンプトが膨張しない」という用途向けの選択肢として位置付ければ、上記の差は **規模に強くするための値段**として理解できます。
